# Optional native still-capture extension

Construction registers the provider before the public world handshake, without reading a session or touching a reply queue. State/session checks remain unavailable until the first validated canonical public stamp; they neither quarantine that initial waiting state nor infer readiness from a reply. Once bound, any loss or change of the public identity quarantines the adapter. It never rebinds or replays automatically.

This experimental extension calls X4's native `capture_screen` action. Its return records dispatch and reservation state; it does not prove that an image exists, that the image depicts the requested subject, or that a camera pose was achieved. It does not record video.

`scripts/live_capture_extension.py` exposes pure `prepare(reference=None)`, returning bytes and a source-bound receipt for exactly `md/X4ToolkitCapture.xml` and `ui/live_capture_extension.lua`. It writes nothing. The loader registers with the existing automation bundle before world bootstrap and requires the canonical public session and MD channel. The provider is `x4-screen-capture-v1`, with fixed `capture` and `release` actions. There is no arbitrary directory, expression, cue or Lua argument.

The default generator records declared native source hashes without claiming that local game files were rechecked. Supplying an explicit reference root verifies the three named source hashes. The working native analogue is `md/terraforming.xml:407–438`; shipped source contains only own-code logic and hashes, not copied game files. A generated receipt does not by itself qualify schema or runtime behavior.

Capture preparation retains the current player container, sector, external-camera state and menu/conversation state. Native execution consumes the request before the call, requires the same retained context and a 4–30 simulation-second preparation window, and retains at most one reservation. Request and transport identities are checked separately. A changed target is observation data, not proof of equivalent framing. Lost or contradictory replies remain uncertain and are not automatically replayed.

The fixed output directory is `x4_toolkit_capture`. Its actual filesystem parent remains a runtime correlation question; observing the native save directory does not prove a screenshot directory. The host `CaptureDispatcher` and `ScreenshotObserver` require the current bound client, exclusive journals, stable decoded image evidence and their own opaque settlement handle. Unresolved captures stay quarantined. `release` clears a native reservation only and always reports `file_completion_qualified=false`; a caller-provided packet cannot mint image evidence. Output files are never deleted by release.

Pre/post `camera_state` samples retain bounded raw read evidence and separate ordered clock domains. They describe sampled orientation/base offset, not target-relative pose, exposure time, continuous visibility or image content. File settlement, camera observations and visual acceptance are distinct claims.

The optional Python decoder is installed with the `capture` extra. Without it, image-dependent controls explicitly skip and the missing-decoder refusal control still runs. Full qualification installs the extra. Public tests cover the pure MD generator, current-source extension bindings, actual SDK/channel/catalog integration with synthetic native endpoints, and all 39 host dispatcher controls. LuaJIT cases run in bounded children so expected protected native exceptions do not flood the parent test log. These are offline controls, not game qualification.
