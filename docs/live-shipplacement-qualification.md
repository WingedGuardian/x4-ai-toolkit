# Diagnostic owned-ship placement

The optional placement extension adds provider `x4-diagnostic-shipplacement-v1` for bounded diagnostic relocation of a helper-issued player-owned operational ship within its prepared current sector. It preserves the existing player-teleport MD and Lua sources. No engine action has been performed to qualify this successor.

`diagnostic_place_ship` accepts exactly `ship`, `x_m`, `y_m`, `z_m`, `yaw_degrees`, `pitch_degrees`, and `roll_degrees`. The last six values are finite numbers; coordinates are sector-relative metres, angles are degrees. Coordinates are bounded to ±10,000,000 m, angles to ±360 degrees and requested displacement to 100 km. The instrument rejects spacesuits, foreign or removed ships, docked ships, assigned docking bays, internal storage, nonoperational targets, a sector different from the player's current sector, or speed over 1 m/s. It does not cancel orders, undock, plan routes or avoid collisions.

Preparation records the exact native object, sector, observed pose, player container/controlled/occupied identities, request and native age. Execution re-resolves the issued identity and consumes the request before `warp`. Native execution rechecks eligibility, context, the ten-second native preparation lifetime, position drift no greater than 1 m and each orientation basis-vector drift no greater than 0.001 m. The separate UI lifetime is also checked after final ID resolution. The two clocks are never equated.

Execution reports a requested warp and its pre-dispatch pose. Only a subsequent native status observation at a strictly later native age can report matching position and orientation. The MD compares its native forward/right/up vectors with the request-derived native rotation vectors, avoiding a guessed Euler conversion. Lua independently verifies the reported vector/position differences. Position tolerance is 1 m and each basis-vector tolerance is 0.001 m. Observed and request-derived values occupy separate fields. A completed SDK request means this bounded pose observation only; it proves no flight, collision safety, sustained position, ordinary docking, rendered view or campaign outcome.

One native unresolved reservation blocks another placement until that same retained request's pose is observed within tolerance or the world is invalidated. Timeouts, lost replies and UI recreation do not free it. Execute is never replayed. A removed/ineligible target after a recorded dispatch yields unknown, retaining dispatch/Busy evidence rather than implying no effect occurred. A post-binding public identity/clock failure permanently faults the Lua owner, including failures detected during native-ID resolution. Late, duplicate, unsolicited, contradictory and malformed replies become unknown. Queue callbacks are retired on disposal; disposal failure remains sticky.

## Source evidence and confidence

READ: `md/terraforming.xml:453–479` uses sector `warp` with position and rotation values; lines 98 and 106 use `create_position` and native `rotation.[yaw,pitch,roll]`. `libraries/scriptproperties.xml:55–64` explicitly distinguishes parent-relative position/rotation from `relativeposition.{sector}` and `relativerotation.{sector}`, and defines cluster-relative speed. Its rotation/vector definitions at 1790–1815 provide native coordinates, distances and forward/right/up vectors; line 2657 specifies constructor yaw/pitch/roll order. The new script copies the native warp shape. It deliberately does not copy the example's random safe-position selection, because this request names an exact diagnostic pose; collision safety stays false.

The shared typed-ID channel follows the native UI event/object-resolution analogues documented in `live-placement-qualification.md`. The target remains exact uint64 cdata through the event boundary; it is not replaced by a decimal string, object name or caller expression. MD resolves and echoes the object; Lua verifies it against the prepared issued ID.

Confidence is 95% for the source-backed action shape, explicit coordinate frame, fixed vocabulary and offline identity/lifecycle controls. Engine preservation of the nested typed ID, vector-unit interpretation and actual achieved pose remain runtime assumptions. The engine must first show this script's LOAD and unconditional TRIGGER markers, then return the exact target/sector and native pose. A failed or ambiguous run does not authorize an automatic retry or an alternative transport.

## Capacity and transport

The fixed `capacity_observe` action accepts empty arguments. Preparation retains one SDK/Lua request but sends no MD event. Execute consumes once and sends one read-only capacity event. Native capacity sampling allocates no placement record and changes no reservation. It reports actual retained MD records, limit, Busy and reply-queue size before its own append, with full native/public correlation. Lua adds its actual request/call counters. Terminal SDK status is historical and does not sample again; a new sample requires a new request.

Interactive/campaign bounds are respectively 128/512 retained Lua requests and native placement records, 1024/4096 Lua transport calls, 64 queued native replies and one pending transport. Failed/refused requests remain counted where allocated. The original player-placement limits remain unchanged. Native records survive UI-only reload and reset on world invalidation. Local Lua counters describe their current owner instance, never an inferred zero native population. Shared SDK/router budgets and the channel's separate 64 outstanding deadline-callback limit also apply. Completed replies do not cancel those callbacks. No whole-campaign capacity guarantee or cross-provider reservation is claimed.

Every native reply validates full request/digest/call/phase, native MD revision and public stamp before delivery. The nested SDK snapshot omits duplicate id/digest/session/public-stamp fields: these are retained by the enclosing SDK receipt and bound router envelope. It retains native revision, call, phase and age. This is a validated compact projection, not the raw MD table. Actual full SDK → router → codec controls include max uint64 target, 512-byte world identity, long numeric poses and complete capacity results under the existing 4096-byte payload-string limit; shared codec limits are unchanged.

## Generation and qualification

`scripts/live_placement_extension.py:prepare(capacity_profile=None)` returns three byte candidates without writing them: the unchanged `md/X4ToolkitPlacement.xml`, new `md/X4ToolkitShipPlacement.xml`, and `ui/live_placement_extension.lua`. The existing descriptor registers the original provider plus the new ship provider. Each channel disposer is registered before fallible provider construction. The loader refuses profile/revision mismatches before acquiring channels. No constructor reads game state or sends requests.

The focused tests use the actual generated loader, LuaJIT SDK, codec, router and public MD channel with synthetic native functions/responses. Native game execution, shared helper composition and deployment are separate qualifications. The canonical MD schema result and final test denominator are recorded in the task receipt; no schema-only result is treated as engine proof.

Final combined ship/player controls passed 112/112 with zero skips, including late encoding, post-dispatch target loss and both capacity limits. Canonical validation compiled both new MD profile variants with zero findings and no skips. A subsequent Lua-only UNKNOWN-status refinement and two controls changed the generated loader revision; exact MD-byte equality preserves the original compiler evidence without another compile. The test source and all twelve directly consumed own-code inputs were hashed before and after the final run. These are offline controls and static proofs, not an engine or complete campaign result.
