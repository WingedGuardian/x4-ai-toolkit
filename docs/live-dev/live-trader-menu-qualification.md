# Built licence and blueprint trader adapter

Offline candidate: current 136 controls pass (81 built-menu + 55 opener); runtime qualification pending. The module operates an already built `BlueprintOrLicenceTraderMenu` and, since 4.2.0, can ask the game to open it in licence mode for a helper-issued faction representative (see "Licence trader opener" below). It never chooses a conversation option. No direct licence grant, blueprint learning, money transfer, or copied game implementation is included.

> The sections after this one are the historical record of the built-menu adapter and keep their original numbers and hashes.

## Licence trader opener (4.2.0)

API: `prepare_open(trader, 'licence')` then the shared `execute(ticket)`; provider action `trader.open {trader, mode}` with `mode` closed to `licence`. The trader token is the one the `representative <faction>` verb issues (`live_query.lua:2096`).

READ vanilla source (reference copy, read only):

- `md/npc_factionrepresentative.xml:272` offers "Show me your licences" with `choiceparam="[0, 0, $FactionRepresentative, 'licence']"`, gated on `not $FactionRepresentative.owner.hastag.nolicencesale`; `:295` opens it with `<open_conversation_menu menu="BlueprintOrLicenceTraderMenu" param="event.param2" .../>`. File SHA-256 `9d18f770939cf16d9f15dbdf14a4e29ffabe7f1b7ab4adbe11df942fab98fba2`.
- `md/diplomacy.xml:944`/`:972` is the same route for a faction diplomat. Not supported by this opener.
- `menu_trader_blueprintsorlicences.lua:1` documents `param == { 0, 0, traderentity, mode }`; `:126-139` takes the trader from `param[3]` (`ConvertIDTo64Bit`) and the mode from `param[4]`. SHA-256 `8715f253…e8f3b`, unchanged from the built-menu read.
- The representative identity comes from `C.GetFactionRepresentative`, declared verbatim from `menu_encyclopedia.lua:101` and called as at `menu_diplomacy.lua:1657`.

Call made: `OpenMenu('BlueprintOrLicenceTraderMenu', Helper.convertComponentIDs({0, 0, trader, 'licence'}))`, the same open shape as `live_textnavigation.lua:259`. Vanilla never opens this menu from Lua; the Lua open replaces the MD `open_conversation_menu`, so the conversation itself is not part of the route. Before dispatch the converted parameters are checked in full, including `param[3]`: it must convert back to the same trader, because a nil or unconverted `param[3]` makes the menu fall back to the player computer as trader (`menu_trader_blueprintsorlicences.lua:127-129`).

Preconditions mirrored, each checked at prepare and again at execute: mode is `licence`; the token resolves as an issued `object`; the trader's owner faction's `GetFactionRepresentative` is that same trader (a ship, station or other NPC token refuses); the faction's `GetOwnLicences` lists at least one `issellable` licence, which is the menu's own row filter (`menu_trader_blueprintsorlicences.lua:304-305`); the trader menu is registered exactly once and not shown; no conversation is active or cancelling (`C.IsConversationActive()` / `C.IsConversationCancelling()`, declared verbatim from `helper.lua:400-401`); no other menu is shown, except Helper's own `DockedMenu` (`Helper.dockedMenu`) or `TopLevelMenu` (`Helper.topLevelMenu`), which vanilla's open path closes itself before showing any other menu (`helper.lua:1383-1391`); the session, generation and UI clock are unchanged, and execute runs within 5 UI seconds of prepare. Every refusal returns `REFUSED` with `action_attempted=false`; a malformed or unissued token is a refusal, not a Lua error.

Why the conversation check: `helper.lua:1402` marks a menu as a conversation menu whenever any conversation is active and not cancelling (see the comment at `:1398`). The trader menu's only close paths (`menu_trader_blueprintsorlicences.lua:623`, `:637`, `:749`) call `Helper.closeMenuAndReturn`, which ends in `ReturnFromMenu` (`helper.lua:1794`). Vanilla uses that return only for conversation-opened menus; `menu_station_overview.lua:5205-5209` takes `Helper.closeMenu` instead when the menu was opened from Lua. Opening outside a conversation therefore means that closing goes through `ReturnFromMenu` with no conversation to return to. **What the engine does then is UNMEASURED** (checklist row 8).

Not mirrored, stated rather than guessed. The faction `nolicencesale` tag: no UI Lua reads faction tags. The census covered all 40 UI Lua files in the reference: 39 in `ui/addons` plus 1 in the only DLC UI folder, `extensions/ego_dlc_ventures/ui`. No `GetFactionData` key names a tag, and the only tag reader found, `HasTag(component, connection, tag)` in `ego_targetmonitor/targetmonitor.lua`, reads connection tags. So a no-sale faction whose `GetOwnLicences` still lists a sellable licence passes. The diplomat route (`md/diplomacy.xml:944`, `:972`) is not supported. Compared with vanilla, the opener is stricter on open menus: only Helper's docked/top-level menu may be up. It is looser on conversation state and on player presence. Vanilla needs a conversation with the representative; the opener requires that there is no conversation and has no presence check, so it may allow a remote licence purchase. That is a design choice and is UNVERIFIED in game.

Reporting: execute returns `DISPATCHED_UNVERIFIED`, `menu_open_verified=false`, `purchase_verified=false`; a native error after the call is `UNCERTAIN`. The open is confirmed only by a later `trader.observe` (`observe(trader,'licence',start)`), which returns `OBSERVED` only when the trader menu is shown, not minimized, in licence mode, for the same trader. A closed, unknown (`shown` not `true`, `minimized` not `false`) or blueprint-mode menu is refused. The opener presses no trader button; buying stays with `prepare_select` / `prepare_confirm`.

## Built-menu adapter (history)

READ source basis: native `menu_trader_blueprintsorlicences.lua` 126–145 binds trader/mode/faction/container; 275–281 creates confirm/cancel; 325–340 creates licence rows; 348–460 creates category and equipment rows; 560–577 creates blueprint rows; 595–678 implements native confirmation and basket mutations. The adapter invokes the actual registered `buttonScriptMap` wrapper after checking cell/row/table/frame and callback identity, following the existing menu adapter mechanism. This is source-backed model binding, not proof of visible pixels or a completed purchase.

API: `observe(trader,mode,start)` returns at most 16 current built rows; `prepare_expand(trader,mode,category,desired)`, `prepare_select(trader,mode,item,price)`, `prepare_confirm(trader,mode,item,price)`, `execute(ticket)`, `dispose()`. Modes are `licence` and `blueprint`. The trader must be an issued object. Confirm requires exactly one selected, currently eligible, named item at the exact positive price. Selection starts from an empty basket. Other basket contents refuse. Category expansion uses the current native button, including a required change from the observed expansion state. No arbitrary callback identifier is accepted.

Dependencies are trusted native wrappers: menus/current/UI elapsed clock/issued resolver/component conversion/widget readers and native `GetPlayerMoney`, `GetUIRelation`, `GetComponentData`, `GetContextByClass`, `GetOwnLicences`, `HasLicence`, `GetWareData`, plus FFI `GetNumBlueprints`/`GetBlueprints`. Component-taking globals need the same exact-ID wrappers as existing native assembly. Construction only declares/checks FFI metadata; it does not query the game. The UI elapsed clock must be `getElapsedTime`, not game time. Parameter ABI is source-declared, runtime unverified.

Before dispatch, all observed model values and native widget references must still agree, with a five-second UI-clock ticket limit. Refusal consumes the private ticket; retries never dispatch twice. Exceptions or lifecycle loss after the wrapper call remain `UNCERTAIN`. `DISPATCHED_UNVERIFIED` never means paid, acquired, rendered, or economically correct. Independent player-state/transaction observations must establish any downstream result.

Limits: 512 built entries/categories, 8192 price-catalogue nodes and native blueprint rows, 512 licences, 128 basket items and preparations. Missing/sparse/duplicate/over-cap data refuses rather than silently narrowing. Blueprint ownership is two equal projected native ware-set reads with equal counts; repeated production-method rows may map to the same ware. This is not an atomic snapshot. Collapsed/hidden catalogue rows are not enumerated; the denominator is only current built rows. Cached funds/relation/ownership drift requires native refresh, rather than silently replacing the menu's price/eligibility state.
