# Bounded host-window clips

`WindowClipRecorder` is a standalone Windows host capability. It does not launch, focus, restore, resize, pause or otherwise control a game. It requires an existing task journal directory, an explicitly supplied FFmpeg executable and its qualified SHA256, and trusted live SessionLink identity and ProfilePeer callbacks. No CLI or native assembly route is installed by this unit. Recording authorization belongs to the calling workflow; constructing a recorder does not grant it.

`prepare(id, duration=10, fps=15)` returns an opaque local handle. Preparation observes one eligible visible, non-minimized top-level window owned by the exact connected X4 process. Win32 independently checks process creation FILETIME, executable path and liveness; PID alone is insufficient. Multiple visible game windows, unreadable window state or unsupported dimensions refuse. `execute(handle)` records once. An exclusive durable consumed journal precedes child creation; errors after consumption quarantine the reservation and never replay. A nonblocking operation lock rejects concurrent/reentrant calls. The task owner cannot reopen an existing journal as a fresh recorder.

The encoder input is a nonzero exact decimal HWND, never desktop or title matching. Standard output goes to an exclusively created task file; the command has no caller-provided options, output protocol, filter or filename. Child execution uses an argument array, no shell, no stdin and a hidden console. Only the recorder's own child is killed on timeout, pipe failure, byte limit or identity drift. During capture and decode the recorder samples canonical load/UI/process/profile identity, window handle/size and the prepared journal. Those samples are not an atomic guarantee between observations.

Bounds: 5–30 seconds, 5–30 requested samples/second, at most 900 decoded frames, 512 MiB per encoded clip, 2 GiB retained encoded clips per recorder (reserve a full per-clip allowance before starting), 128 reservations, 64 KiB child stderr and 2 MiB decoded frame metadata. Capture duration has a 15-second startup/closure allowance; decode has a 60-second timeout. Large or slow captures refuse. Existing evidence is retained, never automatically deleted.

The second FFmpeg pass fully decodes video to SHA256 frame checksums with timestamp passthrough. It checks exact output dimensions, one timebase, strictly increasing decoded timestamps, at least two frames, requested span within one second and maximum gap no greater than max(1 second, four requested sample periods). It records every decoded frame timestamp/hash, actual frame count, distinct hashes and measured gaps. Requested fps and metadata alone are not evidence of delivered frames. The binary and clip are hash-checked before/after decoding.

`DECODED_HOST_CLIP` means a bounded encoded file was produced and decoded under these sampled bindings. It explicitly leaves pixel origin, lack of occlusion, achieved camera pose, motion, compositor timing and visual-case success unverified. Different frame hashes can be a clock, cursor, menu or compression noise; they never automatically pass a motion test. A repeated-frame or black capture can decode correctly and still be useless. An evaluator must inspect the actual clip in its scenario context. GDI and game rendering compatibility, occlusion behavior and DPI scaling remain runtime questions; mismatched decoded dimensions conservatively refuse. No runtime capture has been performed for this implementation.

Source basis (READ): FFmpeg n7.1.1 `libavdevice/gdigrab.c:256–276` accepts HWND and obtains that window DC; lines 551–557 timestamp a capture poll then use BitBlt. These are capture-poll timestamps, not compositor presentation timestamps. FFmpeg's passthrough mode preserves input sample timing rather than deliberately duplicating/dropping frames for CFR; muxers can still alter timestamp representation. The decoder exposes the resulting encoded-file timebase without mapping it to UI or MD clocks. Microsoft GetWindowThreadProcessId/GetClientRect and GetProcessTimes supply the separate host bindings.

- [FFmpeg capture device](https://ffmpeg.org/ffmpeg-devices.html#gdigrab)
- [FFmpeg timestamp modes](https://ffmpeg.org/ffmpeg.html#Advanced-options)

Custom window/child adapters require explicit `synthetic=True`; their receipts remain SYNTHETIC. Tests include a real FFmpeg-generated test pattern through the same encoder/decode contract, never desktop capture. That optional control requires an explicitly supplied `X4_TEST_FFMPEG`; absent dependency is a reported skip, not qualification. Native window enumeration and real game pixel attribution remain untested. No FFmpeg binary is bundled or downloaded.

## Bound client and campaign receipt

`connect_clips(client, profile, journals, ffmpeg=..., ffmpeg_sha256=...)` in `_liveclipport.py` accepts an already-connected production AutomationClient with its actual BoundPipe, SessionLink and ProfilePeer. It neither creates a new world session nor grants recording approval. Two existing, distinct, nonnested task directories named `port` and `recorder` are required; both must be outside the personal profile tree. Before journals are claimed, a real ReadEvidence collection of `native_save_path` must match the explicit profile/save directory and bound stamp. That raw transcript and reader source hashes are retained.

`reserve(case_binding, duration=10, fps=15)` returns an opaque same-owner ticket without recording. The case binding is a declared label, not proof that the intended subject or scene is visible. Within the caller's separately authorized recording scope, `execute(ticket)` performs one recording and returns the same ticket. `receipt(ticket)` verifies unchanged clip, binary, journal, host identity and sources before returning the campaign record. It does not make another native query and explicitly labels the result historical with fresh_current_native_identity=false. `export(ticket)` changes the provenance tier to EXPORTED_UNAUTHENTICATED; serializing a record cannot create a valid local ticket.

During capture/decode, the recorder's identity callback makes the existing supported `bound ping` read. BoundPipe validates the native current stamp, helper build, monotonic native envelope age and actual pipe peer before/after each response. This is necessary because SessionLink.identity alone cannot detect a native load before a new native response arrives. Ping's legacy elapsed-time text is not interpreted or joined to capture/UI/MD clocks. Up to 2,048 sampled envelope records/2MiB are retained per clip; limits refuse and quarantine. No per-poll read-capture cache nonce is consumed. Checks remain sampled; they do not establish an atomic world interval.

The campaign status is CLIP_ARTIFACT_CAPTURED_REVIEW_REQUIRED. It includes the exact helper build, profile/process/load/UI identities, source pins, declared case label, decoded artifact/frame evidence and sampled native envelope records. Visual success, motion, pixel origin, unoccluded rendering and world lineage stay unqualified. Source changes, native/session drift, malformed ping, altered evidence or a failed/ambiguous recording refuse; no retries, automatic reopen or quarantine reset are offered.

The integration controls exercise the actual Lua router, BoundPipe, ReadEvidence and recorder with synthetic native/window/encoder inputs. Production construction rejects that synthetic client. No native recording was run for these controls.
